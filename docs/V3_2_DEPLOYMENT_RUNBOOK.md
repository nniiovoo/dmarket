# V3.2 Deployment & Operations Runbook

This is the operator manual for the v3.2 lane (`EscrowMarketplaceERC20` + `ReputationRegistry`). Sections cover first-time deploy on a fresh testnet, day-to-day operations, healthchecks, troubleshooting, and the mainnet pre-flight checklist.

For the design rationale see [`contracts/v3_2/ARCHITECTURE.md`](../contracts/v3_2/ARCHITECTURE.md).

## 2. First-time deployment (Arbitrum Sepolia, as completed in Phase A–D)

Use this as the template for any future v3.2 deploy on a fresh network.

### 2.1 Prep

1. Fund the deployer wallet with enough ETH on the target network (≥ 0.05 ETH covers the whole flow with margin).
2. Fill in root `.env`:
   ```bash
   PRIVATE_KEY=0x...
   ARBITRUM_SEPOLIA_RPC_URL=https://...
   ```
3. The reputation signer key is generated by the rotation script in 2.3. Don't pre-fill `REPUTATION_SIGNER_PRIVATE_KEY` on a fresh deploy.

### 2.2 Deploy contracts

```bash
npx hardhat run scripts/deployV3_2.ts --network arbitrumSepolia
```

Expected output:

```text
V3.2 marketplace address: 0x...
V3.2 reputation registry address: 0x...
V3.2 mock USD address: 0x...
--- Paste into .env ---
V3_2_ARBITRUMSEPOLIA_MARKETPLACE_ADDRESS=0x...
V3_2_ARBITRUMSEPOLIA_REPUTATION_ADDRESS=0x...
V3_2_ARBITRUMSEPOLIA_MOCK_USD_ADDRESS=0x...
REPUTATION_SIGNER_ADDRESS=0x...    # this one is the orphan; rotate in 2.3
```

Paste the addresses into root `.env` and into `frontend/.env.local` (with `NEXT_PUBLIC_` prefix).

Run `npm run sync-abi` so the frontend picks up the v3.2 ABIs.

### 2.3 Rotate the reputation signer

The Phase A deploy seeds the signer to a derived deployer+1 address whose private key nobody holds. Two-step fix:

```bash
# First run — no signer key in env, script generates one and prints it.
npx hardhat run scripts/rotateReputationSigner.ts --network arbitrumSepolia
```

Paste the printed `REPUTATION_SIGNER_PRIVATE_KEY` + `REPUTATION_SIGNER_ADDRESS` into root `.env`.

Fund the new signer wallet with ≥ 0.001 ETH (for the `acceptSigner` tx; in dev we use `scripts/fundReputationSigner.ts`).

```bash
# Second run — picks up the env, calls setPendingSigner + acceptSigner.
npx hardhat run scripts/rotateReputationSigner.ts --network arbitrumSepolia
```

The script is idempotent — re-running once `signer() == REPUTATION_SIGNER_ADDRESS` exits with `nothing to do`.

### 2.4 Apply DB migrations

v3.2 ships two manual SQL migrations (the project uses `applyManualMigration.ts` rather than `prisma migrate dev` because of a pre-existing sqlite/postgres `migration_lock.toml` mismatch — see the script's header comment):

```bash
cd frontend
npx tsx scripts/applyManualMigration.ts \
  --file prisma/migrations/manual_onchain_order_v3_2.sql
npx tsx scripts/applyManualMigration.ts \
  --file prisma/migrations/manual_published_attestation.sql
npx prisma generate
```

Each apply prints `✓ N/N statements applied.`

### 2.5 Initial catch-up

```bash
cd frontend
npm run indexer:v3_2:once
```

Backfills `OnChainOrderV3_2` from the marketplace's deploy block to chain tip. Should finish in seconds on a fresh deploy (only the constructor + initial `setAcceptedToken` events exist).

If there are already sellers with completed orders, follow up with:

```bash
npm run reputation:cron:once
```

to issue the first round of attestations.

### 2.6 Deploy the Kleros V2 dispute adapter

The adapter bridges `resolveDispute` to the real Kleros V2 court. Once deployed, marketplace ownership is transferred to it — direct EOA `resolveDispute` calls revert from then on.

```bash
npx hardhat run scripts/deployKlerosAdapterV3_2.ts --network arbitrumSepolia
```

Paste the printed `V3_2_ARBITRUMSEPOLIA_KLEROS_ADAPTER_ADDRESS` into root `.env` (and the corresponding `NEXT_PUBLIC_` variant into `frontend/.env.local` once the front-end consumes it). Then transfer marketplace ownership:

```bash
npx hardhat run scripts/migrateV3_2MarketplaceToKlerosAdapter.ts --network arbitrumSepolia
```

The migration script is idempotent: re-running once `marketplace.owner() == adapter` exits cleanly. After this, `cast call $MARKETPLACE "owner()(address)"` should match the adapter address.

For a real end-to-end smoke (creates an order, escalates, costs a few cents in arbitration fee):

```bash
npx hardhat run scripts/smokeKlerosV3_2.ts --network arbitrumSepolia
```

It prints the Kleros case URL — useful for confirming the dispute appears on `v2-testnet.kleros.builders`.

## 3. Day-to-day operations

### 3.1 Indexer

The unified daemon picks up v3 + v3.1 + v3.2:

```bash
cd frontend
npm run indexer
```

For v3.2-only (e.g. backfill on a dedicated worker):

```bash
npm run indexer:v3_2          # daemon
npm run indexer:v3_2:once     # single pass
```

Both honour `INDEXER_CHUNK_SIZE_BLOCKS`, `INDEXER_REQUEST_DELAY_MS`, and the `INDEXER_V3_2_ARBSEPOLIA_FROM_BLOCK` override.

### 3.2 Reputation cron

```bash
cd frontend
npm run reputation:cron       # loops every 15 min
npm run reputation:cron:once  # single pass for cron services / pipelines
```

Production options:

- **systemd timer** invoking `reputation:cron:once` every 15 min — simple, restartable.
- **Vercel cron** — there's a Vercel cron config slot if frontend is hosted there.
- **K8s CronJob** — preferred when frontend already runs on K8s.

### 3.3 Admin tasks

Admin actions live at `/admin` (gated on SIWE + `EVIDENCE_ADMIN_ADDRESSES`).

- **Add / remove accepted tokens**: type the address in the "Accepted tokens" panel → "Stage token" → click the row's "Re-enable" to send the on-chain `setAcceptedToken(addr, true)` tx (or "Remove" for `false`). The connected wallet must be the marketplace owner; non-owner txs revert.
- **Drain refresh queue**: "Refresh all queued (N)" button in the Reputation refresh queue panel — equivalent to one cron run, but only over queue entries with `processedAt = null`.
- **Propose / accept signer rotation**: same flow as 2.3 but driven from the UI. Phase D's `scripts/rotateReputationSigner.ts` stays available for headless ops.

### 3.4 Updating the score formula

Edit constants in `frontend/lib/reputation/score.ts` (`SCORE_BASE`, `DISPUTE_PENALTY`, etc.). No contract change required — next cron run produces attestations with the new formula. `MIN_SAMPLE_SIZE` is gating UI display, not the formula itself.

## 4. Healthchecks

### 4.1 Indexer status

```bash
curl http://<host>/api/indexer/status
```

Expected response includes a `v3_2` block:

```json
{
  "chains": [...],
  "v3_2": {
    "chainId": 421614,
    "marketplaceAddress": "0xFf488C9bE6ec21AC47368bed321F4aAa62bAbCA1",
    "lastIndexedBlock": "26869...",
    "currentBlock": "26869...",
    "lagBlocks": 12,
    "lagSeconds": 3,
    "orderCount": 10,
    "status": "healthy"
  }
}
```

Alert when `lagSeconds > 60` for 5 consecutive minutes.

### 4.2 Reputation API

```bash
curl http://<host>/api/reputation/<sellerAddress>
```

Expected: `onChain` non-null for any seller the cron has processed at least once. `cached.score` always present; `sampleSize` reflects the seller's full ChainUs order history.

### 4.3 On-chain spot checks

```bash
# Current signer (should match REPUTATION_SIGNER_ADDRESS in .env)
cast call $REPUTATION_REGISTRY "signer()(address)" --rpc-url $ARBITRUM_SEPOLIA_RPC_URL

# An accepted token (should return true)
cast call $MARKETPLACE "acceptedToken(address)(bool)" $MUSD --rpc-url $ARBITRUM_SEPOLIA_RPC_URL
```

(Or via Arbiscan's "Read Contract" tab.)

## 5. Troubleshooting

### 5.1 Indexer is lagging

- **Public RPC throttling.** Symptom: `eth_getLogs` 429s in indexer log. Switch `ARBITRUM_SEPOLIA_RPC_URL` to a paid Alchemy / Infura endpoint. Adaptive chunk halving in `getLogsAdaptive` already handles block-range overruns; rate limits are different.
- **Cursor stuck mid-batch.** Inspect `IndexerStateV3_2.lastBlock` for the chain. If it's stale, the daemon may have crashed inside `processLogsV3_2` before advancing. Re-run `npm run indexer:v3_2:once` — it picks up from `lastBlock + 1`.
- **Reset checkpoint.** To re-index from a specific block:
  ```sql
  UPDATE "IndexerStateV3_2"
  SET "lastBlock" = <block> - 1
  WHERE "chainId" = 421614
    AND "marketplaceAddress" = lower('0xFf488...');
  ```

### 5.2 Cron `recordAttestation` fails

- **`InvalidSigner` revert.** The on-chain signer doesn't match `REPUTATION_SIGNER_PRIVATE_KEY`. Compare `cast call $REGISTRY "signer()"` with the env address. Re-run the rotation script if needed.
- **`VersionNotIncreasing` revert.** A different cron / smoke script published a higher version concurrently. Wait one cron cycle; the issuer's next `latest()` read picks up the new version and increments past it.
- **`Nonce provided ... lower than current`.** Public RPC nonce lag — `publisher.ts` already waits for receipts, but two relayer processes against the same key will collide. Make sure only one cron / refresh-queue runner is active at a time.
- **Signer wallet out of ETH.** Check `getBalance(REPUTATION_SIGNER_ADDRESS)` — top up via `scripts/fundReputationSigner.ts` or any wallet.

### 5.3 `setAcceptedToken` rejected

- Connected wallet must be the marketplace owner (`cast call $MARKETPLACE "owner()(address)"`). Non-owner txs revert with `OwnableUnauthorizedAccount`.
- `address(0)` is rejected — the contract requires a non-zero token. Frontend already validates this.

### 5.4 Compromised deployer key (emergency)

If `PRIVATE_KEY` is suspected to be leaked:

1. Immediately call `pause()` on the marketplace from any signer that still controls the owner key (don't lose the race). Once paused, `payOrder` / `markShipped` / `confirmReceived` / etc. all revert with `EnforcedPause`. Disputed orders can still be resolved (after the 3-day delay).
2. Transfer ownership of both `EscrowMarketplaceERC20` and `ReputationRegistry` to a fresh wallet via `transferOwnership` (`Ownable2Step` — the new wallet must `acceptOwnership` to complete).
3. Reissue the reputation signer key via `setPendingSigner` + `acceptSigner` from the rotated owner.
4. Update `.env` everywhere.

There is no way to undo escrowed orders that have already paid out — the on-chain delays (`DISPUTE_RESOLUTION_DELAY = 3 days`, `markShipped` requires `Paid` state) are the only buffer.

## 6. Mainnet pre-flight checklist

v3.2 is testnet-only today. Before any mainnet deploy:

- [ ] Third-party audit of `EscrowMarketplaceERC20` + `ReputationRegistry` + the off-chain attestation pipeline (`issuer.ts` / `publisher.ts` / cron).
- [ ] Multisig (e.g. Gnosis Safe, 2-of-3) accepts ownership of both contracts via `transferOwnership` → `acceptOwnership`. Apply a Timelock controller in front of the multisig for high-stakes operations.
- [ ] **Transfer `KlerosV2DisputeAdapterV3_2` ownership to the same multisig + Timelock.** Until then, the EOA adapter owner can call `executeOnMarketplace(resolveDispute…)` and bypass the 30+7 day emergency timelock. Multisig + Timelock turn that backdoor into a publicly observable, delayable action.
- [ ] Replace public RPC with a paid Alchemy / Infura tier on the indexer and relayer hosts. (The `publisher.ts` receipt-wait workaround can stay; cost is one extra round-trip per attestation.)
- [ ] Replace the in-memory rate limiter in `frontend/lib/rateLimit.ts` with Redis (or Upstash). Affects `/api/reputation/[address]` and any other endpoint sharing the limiter.
- [ ] Observability: Prometheus / Grafana metrics for indexer lag, cron success rate, attestation publish latency. Pager alert on `lagSeconds > 60` and on `failed > 0` in the most recent cron run.
- [ ] Production-grade key custody for `REPUTATION_SIGNER_PRIVATE_KEY` (HSM or KMS). The attestor key signs every score that goes on-chain; a leak lets an attacker mint arbitrary attestations.
- [ ] Decide whether to keep `MockERC20` accepted-token entries. On mainnet only real stablecoins (USDC / USDT / DAI) should be allowlisted.
- [ ] Frontend audit: confirm no `0xFf488…` testnet addresses or test private keys remain in committed `.env*`. Run `git grep '0x[a-fA-F0-9]\{40\}'` against the runtime env.
